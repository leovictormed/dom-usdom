ETAPA652 — PREACTIVATION CEREMONY AND ARTIFACT BINDING
Date: 2026-10-23

Scope
- Audited production-preactivation-core and its fixed materialization wrapper.
- Reconciled ETAPA651 checkpoint guardian owner identity and the later ETAPA661
  bounded ERC20 reserve bytecode.
- No production template was materialized and no external action was performed.

Findings and corrections
1. The preactivation producer derived adapter runtimes but did not retain their
   initcode hashes. It now obtains each adapter runtime, initcode and config hash
   from one source-verified artifact binding and materializes both verifier
   initcode pins together with their runtime/config pins.
2. Finalized-burn and checkpoint adapter bindings independently recompute the
   expected immutable configuration and reject a supplied stale config hash.
3. One canonical ordered three-owner list now derives the governance, reserve
   guardian and checkpoint guardian commitments. A reordered or substituted
   list cannot preserve the authorized checkpoint registry identity.
4. DOMCheckpointRegistry's control-plane typehash and config hash now include
   guardianOwnersCommitment. The Node derivation, runtime immutable patching,
   initcode/config derivation, readiness, submission, reproducible-build,
   solidity-pin, release-core and preactivation consumers use the same field.
   A non-Safe test control contract is represented exactly as Solidity does by
   bytes32(0); production release validation still requires the canonical
   nonzero Safe commitment.
5. The fixed wrapper hashes the release template before preparation and checks
   it again under the config-directory flock immediately before durable install.
   Existing assign/cmp/install behavior remains fail-closed and idempotent.
6. Native preactivation facts remain exact-schema inputs: the Ethereum trusted
   checkpoint, DOM domain/network/chain, activation predecessor, checkpoint
   cadence and total-work anchor are reconciled before the registry pin. Empty
   state root, activation schedule and reserve final config stay unset until
   their dependent post-compilation phase.
