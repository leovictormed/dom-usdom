USDOM native Ethereum consensus configuration binding — stage 245
Date: 2026-10-20
Severity closed: High (USDOM-245)

Problem

The native runtime manifest was hash-pinned and its checkpoint/deposit policies
were reconciled with the Ethereum release, but its eight Ethereum fork entries
could contain any canonical-looking epochs and versions. The trusted
weak-subjectivity checkpoint was required to be nonzero by the static policies,
yet no release field identified the checkpoint approved for this release. A
signed manifest could consequently select a stale or substituted Ethereum
consensus view without the release gate detecting the semantic change.

Correction

1. The DOM mainnet loader now accepts only Ethereum mainnet's canonical genesis
   validators root and the supported fork schedule:
   Genesis 0/00000000; Altair 74240/01000000; Bellatrix 144896/02000000;
   Capella 194048/03000000; Deneb 269568/04000000; Electra 364032/05000000;
   Fulu 411392/06000000; Gloas uint64-max/07000000.
2. Non-mainnet networks retain explicit schedules for deterministic testing.
3. The runtime bundle and offline checker export the trusted checkpoint and all
   eight epoch/version pairs.
4. The exact 53-field production release schema adds
   nativeEthereumTrustedCheckpoint as a mandatory nonzero bytes32 value.
5. Readiness compares that release value with checker output and independently
   checks every exported fork value against the supported mainnet schedule.
6. The closed-mainnet requirement
   production_native_ethereum_consensus_config_release_bound records this
   invariant.
