NATIVE USDOM ISSUANCE FROM AN ETHEREUM-FINALIZED DEPOSIT — STAGE 61
Date: 2026-10-17
Status: isolated Regtest implementation; not approved for production, deployment, or real funds

OBJECTIVE

Remove an independent mint authority from native USDOM issuance. A node may now
accept an issuance envelope only by replaying a bounded Ethereum light-client
transcript, authenticating the exact USDT reserve deposit receipt and reserve
post-state/code, and converting the opaque result under consensus-owned policy.
Transfer and burn proof kinds remain fail-closed.

IMPLEMENTED PATH

1. UDOMDPW1 is the canonical bounded deposit witness. It contains the exact
   canonical light-client transcript, the externally committed finalized
   execution identity, and canonical JSON evidence for execution ancestry,
   receipt inclusion, reserve account/code and the Deposited event. Framing,
   component lengths and total size are bounded before cryptographic replay.
2. DepositTrustPolicy pins Ethereum chain ID 1, Beacon genesis, weak-subjectivity
   checkpoint, fork schedule, reserve address, runtime code hash, bridge domain,
   and maximum accepted deposit amount. The DOM block timestamp supplies the
   only admissible current-slot ceiling. That dynamic ceiling is excluded from
   the immutable policy hash.
3. Direct local deposit composition carries a zero trust-policy hash and cannot
   authorize native issuance. Only full witness replay installs the exact
   deposit-policy hash in the opaque VerifiedDeposit.
4. The native BridgeIdentity and StateCommitment include that deposit-policy
   hash. Startup, snapshots, direct extensions, retained side branches and
   reorg promotion therefore require the same immutable issuance policy.
5. The initial note commitment is derived deterministically from version,
   bridge domain, deposit-policy hash, Beacon genesis, event block and position,
   deposit ID, funder, exact uint64 amount and receiver commitment. A relayer
   cannot substitute a value or choose an unrelated note. No issuer signing key
   or operator quorum appears in this path.
6. The existing state machine atomically enforces one-time deposit consumption,
   note uniqueness, supply accounting, Ethereum-anchor consistency, persistence,
   undo and reorganization behavior.

FINALITY SEMANTICS

The event may occur in an execution block earlier than the retained finality
head. Receipt/account/code proofs bind to the event block through authenticated
execution ancestry. The issuance EthereumAnchor records the complete later
finality head (execution number/hash/timestamp and Beacon slot/root), not a
synthetic mixture of the event header and finality metadata. Multiple historical
deposits may therefore share one valid later finality anchor without conflict.

FORMAT MIGRATION

The bridge/state commitment gained a deposit-policy hash, so old experimental
state must not be interpreted under the new monetary identity. Canonical state
keys are now usdom/v2, the burn-state witness is USDBRN02, and UDSNAP01 is
version 3 with manifest tag v3. No automatic migration grants authority to old
state. A future reviewed activation/migration procedure remains required.

PRIVACY BOUNDARY

The Ethereum deposit, amount, funder and reserve are public. Stage 61 derives a
one-time initial native note from that public occurrence and a receiver
commitment. This does not by itself provide private transfer or burn semantics.
A reviewed proof system must prove ownership, note membership, ranges, exact
conservation, nullifier correctness and public burn obligations while using the
same frozen commitment relation. A trusted single-party Groth16 setup from the
reference laboratory was deliberately not imported.
