USDOM stage 399 — Safe singleton identity pinning
Date: 2026-10-22

Finding
=======

The reserve and checkpoint registry pinned each administrative Safe proxy's
runtime code hash, while Safe stores its mutable singleton implementation in
proxy storage. A supported Safe migration can therefore change masterCopy()
without changing the proxy runtime code hash. Finalized off-chain Safe evidence
observed the singleton, but the contracts did not continuously enforce it.

Correction
==========

USDOMProofReserve now captures and commits the governance and guardian
implementation address and implementation code hash. DOMCheckpointRegistry
does the same for its guardian. Direct non-proxy contracts remain supported by
binding the account itself as its implementation. Safe-style proxies are
recognized through an exact, bounded, 32-byte masterCopy() STATICCALL.

Every reserve value path and delayed resume rechecks both proxy and singleton
identity. The permanent checkpoint halt rechecks the same identity. Invalid,
changed or missing implementation state fails closed. The typed deployment
commitments now include ControlPlaneIdentity hashes, so the singleton cannot be
substituted between reviewed configuration, initcode and deployed runtime.

The SDK, runtime derivation, checkpoint/finalized-burn submission builders,
release schema, Safe materializer, preflight collector and readiness gate carry
the same identities. Preflight reads all three masterCopy() values and all
three implementation code hashes at one finalized Ethereum snapshot.
