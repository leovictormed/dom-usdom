Stage 307 — source-bound native evidence and governance release authorization
Date: 2026-10-22
Status: implementation validated locally; no production ceremony or publication

Findings

The release gate validated four release-bound native attestations through
EIP-1271, but it did not provide a fixed way to derive, sign and materialize
those documents. The residual-risk object also named governance without proving
that the governance Safe had approved production, deployment, real funds and
the exact report. Manual JSON editing could therefore claim authorization.

Corrections

One shared finalized EIP-1271 collector now checks chain identity, pins one
finalized block, authenticates governance runtime code, requires the exact ABI
bytes4 magic value and re-reads the pinned block hash. Native attestations keep
their existing interface but use this shared primitive.

The release authorization is EIP-712 domain-separated by Ethereum chain ID and
the exact governance contract. Its message binds release ID, source commit,
reserveConfigHash, checkpointRegistryConfigHash, residual-risk report SHA-256,
acceptance timestamp, governance and three explicit true bits for production,
deployment and real-funds authorization. Readiness recomputes this digest and
requires a successful finalized EIP-1271 observation whose code hash and time
match the release.

The deterministic risk-report writer binds the release identity, immutable
configurations, operating limits, approved finality, the complete pre-acceptance
evidence envelope and all twelve documented risk classes. It labels every risk
unaccepted; only the later Safe signature changes operator authorization.

Fixed commands now derive four native signing requests from the source-built
runtime checker and the reconciled TPM custody/public-identity/recovery records.
Two governance Safe owners sign each raw digest on Ledger, in canonical owner
order. Finalized EIP-1271 validation occurs before four immutable attestation
documents and their metadata are published. The same two-owner ceremony signs
the final release authorization only after the native documents and risk report
exist. Filesystem writers use owner-only directories, exclusive locks, direct
files, fsync, immutable replacement checks and completion metadata last.

Authorization boundary

No command invents a signer or lowers the production 2-of-3 Safe threshold.
The signing scripts require an interactive phrase and two matching hardware
owners. Request generation, validation and materialization contain no Ethereum
transaction publication, deployment, fund movement, Git commit, tag or push.
This implementation does not authorize a release by itself.
