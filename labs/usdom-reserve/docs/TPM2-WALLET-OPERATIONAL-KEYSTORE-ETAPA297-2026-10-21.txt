USDOM stage 297 - TPM2 operational wallet keystore
Date: 2026-10-21

Finding
=======

The deterministic recovery seed backup was protected by Argon2id and
authenticated encryption, but the same human recovery password also encrypted
every live wallet snapshot. The stage-296 TPM authority detected filesystem
rollback; it did not keep the operational decryption key behind hardware. A
copied snapshot plus its recovery password was therefore enough to expose the
active wallet secrets without the original host TPM.

Implemented correction
======================

1. A second fixed TPM2 NV index, 0x01555345, stores a random 256-bit wallet
   pepper inside a canonical wallet/release-bound USWKEY01 record. The record
   includes the fixed index, exact release/network/wallet binding and an
   internal domain-separated SHA-256 digest.

2. The index has an independent random 256-bit authorization. Its credential is
   stored in an authenticated create-only envelope encrypted with the recovery
   password and bound to the index and release/wallet identity. Authorization is
   passed to tpm2-tools only through an inherited anonymous memfd.

3. The operational snapshot password is HKDF-SHA256(recovery password, TPM
   pepper, domain plus exact binding), encoded as a fixed 64-character secret.
   Neither factor alone is sufficient. The password has no public accessor and
   can be emitted only to a create-only 0600 file in a direct current-user 0700
   directory. The fixed commands use a fresh child directory of /dev/shm and
   delete it on exit.

4. Provisioning authenticates the release manifest, privacy policy, encrypted
   recovery backup and complete public wallet identity before defining or
   reopening the index. It rereads the exact TPM record, exercises the KDF
   without exporting the password and publishes create-only evidence binding
   the manifest, chain, wallet, TPM record commitment, recovery ciphertext,
   public identity and encrypted credential.

5. Unlocking repeats the complete backup/address validation, authenticates the
   evidence and live TPM record, then creates the ephemeral operational-password
   file. It does not accept TPM owner authorization and cannot provision,
   submit, mine or broadcast.

6. The registration command now accepts separate recovery and state password
   files. Only the recovery password decrypts the portable seed; only the
   TPM-derived operational password encrypts generation 1. Observation,
   private-burn preparation, TPM authority bootstrap and burn submission now
   unlock the same TPM keystore and pass only the derived operational password
   to snapshot code.

Crash and substitution behavior
===============================

- A fully initialized index is never overwritten after a read or authentication
  failure.
- A crash after NV definition but before the first write is recoverable only
  with the exact encrypted authorization credential.
- An existing written record with a wrong binding, digest, size, algorithm,
  attributes or authorization fails closed.
- The public-area read explicitly selects device:/dev/tpmrm0 and distinguishes
  the exact unwritten and written attribute sets.
- Output creation rejects pre-existing paths and unsafe parent ownership or
  modes. Every downstream command deletes the temporary password directory.

Trust and recovery boundary
===========================

Stage 317 clarification (2026-10-22)
===================================

The implementation claims below are now true because the hardware-backed
keystore, monotonic authority and recovery command paths exist and have concrete
dependency checks. This does not claim that this host exercised a live TPM or
completed the release ceremony. Those operational facts remain separately false
and the real-funds gate still requires the hash-bound custody and recovery
attestations.

The portable recovery backup intentionally remains usable without this TPM;
otherwise TPM loss would destroy the wallet itself. Loss or clear of the TPM
makes existing operational snapshots unavailable. Recovery must restore the
seed, reconstruct authenticated DOM history into fresh state and provision a
new TPM keystore. A live disaster-recovery exercise is still required before
release and is represented by separate operational evidence rather than by an
implementation flag.

Validation
==========

- TPM wallet/authority unit tests: 7 passed, including record corruption,
  binding, two-factor derivation, two-phase CAS and memfd inheritance.
- Keystore binary release parser test: passed.
- Strict release Clippy across the keystore, registration, observation, burn
  builder, authority bootstrap and submission binaries: passed.
- Fixed-command policy tests: 41 passed.
- Shell syntax checks passed for provisioning and all five migrated commands.

No live TPM state was touched because tpm2-tools and current-user tss access are
still absent. No node, miner, prover, Ethereum transaction, deployment, funds or
remote push was used. External-audit absence and an impossible zero-risk
guarantee are not blockers; missing live hardware and recovery evidence remain
objective blockers.
