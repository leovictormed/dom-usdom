ETAPA 989 — mainnet operational daemon secret boundary
Date: 2026-10-23

Scope
Reviewed the long-lived credential-bearing RPC proxy and its two production launchers for provider
URLs/tokens in argv, inherited environment, stdout/stderr, status JSON, core dumps and files.

Concrete finding
The deployment and Safe-recovery shells removed known debug/proxy variables and disabled xtrace and
core dumps, but the background `timeout` and Node proxy still inherited every unrelated exported
operator variable for up to 24 hours. That needlessly exposed cloud credentials, agent sockets and
other secrets through the daemon environment. Direct proxy invocation could also bypass the shell's
core/debug controls.

Correction
- Both launchers now place the timeout and Node daemon behind `env -i`, passing only HOME, fixed
  PATH, one one-shot hardened-launcher marker and the path to the owner-only RPC source file.
- The RPC provider URLs/tokens remain exclusively in the 0600 runtime file; neither secret content
  nor its path enters argv. The runtime helper deletes the path variable immediately after capture.
- The proxy rejects direct invocation without the hardened marker and deletes the marker at startup.
- Provider/upstream failures remain fixed redacted diagnostics; stdout/stderr contain no source URL.
- The public RPC catalog now uses fatal UTF-8/strict JSON bytes rather than tolerant string decode.
- Existing 0600 O_EXCL readiness file, ephemeral loopback capability, bounded channels, signal
  cleanup, parsed-object clearing, `ulimit -c 0`, `set +x` and private temporary directory remain.

Verification
- Focused daemon/runtime-secret suites: 6/6 pass.
- Node syntax, both shell syntax checks and git diff --check: pass.
- No proxy, RPC, deployment, signing, build, commit or push was executed.
