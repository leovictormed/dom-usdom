ETAPA1017 — native USDOM wallet randomness, nonce and secret lifecycle
Date: 2026-10-23

Result
No concrete key-recovery, nonce-reuse or retry-linkability flaw was found. Added a permanent lifecycle gate.

Findings
- Production APIs require caller RNGs implementing both RngCore and CryptoRng. Wallet recovery roots, owner secrets, note rho values, X25519 ephemeral keys, XChaCha20 nonces, Groth16 prover randomness and burn request IDs all consume that CSPRNG. Invalid/zero field samples are rejected and resampled; request IDs use a fixed failure budget and reject zero, burn-ID and pending collisions.
- Recovery uses HKDF-SHA256 with a fixed protocol salt, different owner/scan purpose strings, exact chain scalar and retry counter. Owner and scan roles therefore cannot share derived bytes, and restoring the same encrypted seed deterministically restores only the intended long-lived identity.
- Each memo entry receives a fresh ephemeral X25519 secret and 192-bit XChaCha nonce. The AEAD context binds chain, owner, scan public key, ephemeral public key, note commitment and output index. Duplicate (ephemeralPublic, nonce) pairs in one memo fail closed.
- Transfer and burn outputs draw fresh independent rho. Input nullifiers are deterministically bound to chain, owner secret and note commitment; transfer and burn cannot assign a new nonce to the same input. WalletState accepts one mutable builder at a time, reserves selected commitments before exposing a pending intent, and prevents simultaneous burn/transfer selection.
- Network submission requires an encrypted snapshot containing the exact randomized payload, an external monotonic seal, and a submission permit. Snapshot file locks, expected prior seals, reconciliation and no cancellation after authorization make retry/crash recovery resend exact bytes instead of regenerating a linkable alternative.
- Recovery backups are AEAD encrypted, chain-bound, created no-clobber and restored from one captured byte snapshot. Snapshot locks serialize concurrent writers. Stale or rolled-back reservations remain conservative until canonical reconciliation.
- Recovery seeds, passphrases, scalar sample buffers, plaintext memos, private openings and circuit witnesses use Zeroizing/ZeroizeOnDrop. WalletSecrets is intentionally non-Clone/non-Debug/non-Serialize. Public summaries expose commitments/nullifiers/payload IDs only; no owner secret, rho, scan secret or plaintext is logged.

Residual implementation fact
Built payloads and encrypted snapshots necessarily contain public nullifiers and ciphertext and can be copied as ordinary Vec bytes. This is required for deterministic resubmission and does not reveal note openings. Rust zeroization cannot guarantee erasure of compiler/runtime copies outside the explicitly protected types; no such copy is used as a recovery authority.

Permanent gate
scripts/check-private-wallet-secret-lifecycle.py locks CSPRNG trait bounds, domain-separated HKDF recovery, AEAD nonce/ephemeral uniqueness, zeroizing secret types, pre-submission reservation, durable snapshot permits and file locking.
