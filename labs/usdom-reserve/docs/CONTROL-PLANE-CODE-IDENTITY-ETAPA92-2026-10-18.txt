Control-plane runtime-code identity — etapa 92
Date: 2026-10-18
Status: isolated implementation; mainnet configuration and authorization remain absent

Finding USDOM-092

Severity: High for a production deployment.
Current public exposure: none; no transaction, commit, tag, push or deployment was made.

The immutable reserve configuration bound the governance and guardian addresses
but did not bind their deployed runtime code. A role contract could therefore be
destroyed and recreated with different code at the same address, or otherwise
change runtime code on a network that permits it, without changing the committed
reserve policy. Value paths would continue to trust an identity different from
the one reviewed before release.

Remediation

USDOMProofReserve now captures governance.codehash and guardian.codehash during
construction and includes both in ReservePolicy and reserveConfigHash. Deposit,
proof admission, payout, resume scheduling and resume execution all compare the
live extcodehashes with the immutable values and revert with ControlPlaneChanged
on any mismatch. Construction already requires both roles to be distinct
contracts, so the committed hashes cannot be the empty-account code hash.

The SDK and fail-closed mainnet release gate independently require and reproduce
both role code hashes. The unconfigured manifest keeps both fields null, adding
two explicit blockers until actual reviewed deployments exist. The prior etapa
86 policy vector is superseded by this code-identity-bound vector:

Security boundary

An extcodehash identifies runtime bytecode, not mutable state behind that code.
In particular, a proxy or Safe can keep the same runtime while changing its
implementation, owners, threshold, guards or modules. Production role custody
therefore still requires exact configuration evidence, independent review and
live preflight checks. The generic contract cannot safely infer those semantics.
