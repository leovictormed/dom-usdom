USDOM stage 400 — Safe runtime policy pinning
Date: 2026-10-22

Finding
=======

Stage 399 continuously authenticated each administrative Safe proxy and its
singleton implementation, but identity alone did not prevent an authorized or
compromised Safe transaction from lowering its threshold or enabling a module.
Either change could weaken the authority without changing proxy or singleton
bytecode. Owner recovery also requires owner identities to remain mutable, so
pinning a static owner set would make the reviewed one-key recovery path fail.

Correction
==========

USDOMProofReserve and DOMCheckpointRegistry now recognize a Safe-style control
only when masterCopy(), getThreshold(), getOwners() and getModulesPaginated()
all return exact bounded canonical ABI. Safe controls must continuously retain:

- threshold exactly 2;
- exactly three distinct, nonzero, canonical owners; and
- no enabled modules.

Every call is a STATICCALL with an independent 50,000-gas cap and a fixed
maximum return size. Oversized, malformed, unavailable or inconsistent policy
data fails closed. Direct immutable control contracts remain supported and do
not impersonate the Safe interface. Owner addresses are intentionally allowed
to rotate while the 2-of-3 structure remains intact, preserving the reviewed
loss-of-one-key recovery procedure.

Reserve value paths and delayed resume now reject policy drift with
ControlPlaneChanged. Permanent checkpoint halt rejects it with GuardianChanged.
Construction rejects a Safe that is already below threshold, has the wrong
owner count or has a module enabled. Emergency reserve pause remains available
as its existing safety action even after control-plane drift.
