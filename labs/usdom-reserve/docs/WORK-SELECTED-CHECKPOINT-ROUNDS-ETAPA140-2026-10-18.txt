Work-selected checkpoint rounds — Stage 140
Date: 2026-10-18
Status: registry selection protocol implemented and tested; production proof program absent

Critical defect corrected

The previous registry finalized the first proof-authorized extension received by
Ethereum. A proof that one DOM branch is valid does not prove that the branch is
the canonical highest-work branch. An adversary able to construct and submit a
valid side branch first could therefore make Ethereum irreversibly accept the
wrong checkpoint even though honest DOM nodes preferred another branch.

Final protocol

1. Every round targets exactly latestHeight + checkpointInterval. The interval
   is immutable, nonzero and at most 360 blocks.
2. A public statement includes cumulative total difficulty at the ratified
   predecessor, the target checkpoint and a fixed confirmation suffix.
3. The suffix ends exactly confirmationDepth blocks after the target. All
   candidates for one round are therefore compared at the same DOM height.
4. A candidate must prove strictly increasing cumulative work at both the target
   and suffix. The future production proof program must recompute every header,
   expected target, RandomX result, per-block difficulty, total difficulty,
   ancestry, ordinary consensus rule and native USDOM transition.
5. During an immutable Ethereum challenge period, a candidate is replaced only
   by greater confirmation total difficulty. Equal-work branches use the same
   lower-block-hash deterministic tie-break as DOM fork choice.
6. Replacement does not reset the deadline, preventing an endless sequence of
   valid improvements from extending the round. Replacement closes at the exact
   deadline, so a withheld branch cannot arrive and be finalized in the same
   instant without the configured observation window.
7. Only permissionless finalizeCheckpoint after the deadline updates the
   ratified head and emits Checkpoint. Candidate submission emits a distinct
   CheckpointCandidate event that the finalized-burn witness cannot consume.
8. The permanent guardian halt blocks both submissions and finalization. It
   cannot choose a candidate, forge a proof, move the head or resume the system.

Identity and release binding

checkpointInterval, confirmationDepth, challengePeriod and the bootstrap total
difficulty are committed into checkpointConfigHash, constructor initcode,
runtime immutable checks, the release manifest and the finalized mainnet
preflight. A cold start requires the exact bootstrap total difficulty and an
empty pending candidate. The checkpoint verifier manifest cross-checks the same
interval, suffix depth and challenge period and requires maxCheckpointSpan to
equal interval + depth.

The incompatible public statement is explicitly versioned UDCPST02. It is 442
bytes and its v2 manifest commits the new Solidity type hash, v2 prover input,
fork-choice rules, PoW rules, native state rules, proving program, verification
key, verifier artifact and proof ceiling. Reusing UDCPST01 would have allowed an
old parser to misidentify the new wire format, so version 1 was retired.

Validation performed

- Solidity: 116 tests passed, including 12 registry tests, 1,024 registry fuzz
  cases and 49,152 invariant calls across the reserve suites.
- Node: 55 tests passed, including a deployed Anvil candidate/finalization flow,
  deterministic runtime/initcode derivation, release gates and mainnet preflight.
- Rust public statement: 4 tests passed; clippy completed with warnings denied.
- Dependency firewall: UDCPST02 has eight normal dependency packages and no DOM
  node, storage, RandomX host, async or RPC authority.

Security assumptions and remaining blockers

The result is still probabilistic PoW checkpointing, not mathematical proof that
no stronger hidden branch exists. Safety depends on the configured suffix depth,
Ethereum transaction inclusion during the challenge period, observers submitting
the best known branch, the verifier correctly enforcing DOM consensus and the
usual DOM PoW assumption. Ethereum censorship for the entire challenge window or
a stronger private DOM reorganization after the suffix remains a risk. Parameter
selection must quantify these risks from measured DOM block and reorganization
data.

The repository still has no production consensus-extension guest/circuit, no
production Solidity verifier or verification key, no reproducible proof artifact,
no ratified mainnet bootstrap values, no positive proof generated by the selected
backend, no independent cryptographic/Solidity audit and no production operator
authorization. The production constants remain zero and Ethereum chain ID 1
deployment fails closed. This stage does not authorize deployment or real funds.
